Часть 1 — критика промта №1 (архитектор/COO контент-завода).

## Часть 1. Критика промта №1

### 1.1. В одном промте склеены три несовместимых артефакта

Внутри лежат одновременно:

- **политика** — зоны A/B/C, уровни риска, запреты, гейты (документ, который меняется раз в квартал);
- **проектное задание** — «спроектируй конвейер, определи агентов» (разовая работа);
- **операционная процедура** — «отвечай в формате из 12 секций», «не переходи к новой задаче без подтверждения» (поведение на каждом ходу).

Практическое следствие: **на каждом ходу модель заново выводит устройство завода вместо того, чтобы выполнить текущий шаг.** И формат ответа §10 обязывает выдать 12 секций даже там, где содержательный ответ — «запись готова, следующий шаг — Gate 6, критерий Done — просмотр финального мастера». Промт, спроектированный ради снятия рутины с автора, гарантированно производит церемонию на каждом взаимодействии.

Разделять на: `POLICY.yaml` (машиночитаемая политика), `SPEC.md` (разовый проект), `operator.md` (тонкий рабочий промт).

### 1.2. Система без состояния — главная ошибка

§9 требует таблицу из ~20 полей статуса на выпуск, §12 требует не двигаться дальше без подтверждения человека. Но у модели нет долговременной памяти: в следующей сессии она восстановит статусы из того, что окажется в контексте, то есть **придумает их**. Трекер производственного процесса не может жить в голове модели.

Состояние должно лежать в файле (`state/issue-NNN.yaml`), а промт должен уметь только **читать и изменять** его, никогда — помнить. Это единственная правка, без которой всё остальное не имеет смысла.

### 1.3. Две противоречащие таблицы полномочий

§1 задаёт зоны A/B/C по типу задачи, §7 задаёт уровни риска по тому же материалу — и они расходятся:

| Артефакт | §1 (зоны) | §7 (риск) | Противоречие |
|---|---|---|---|
| Переводы | B — обязательное утверждение | средний — выборочная проверка | да |
| Заголовки | B — обязательное утверждение | средний — выборочная проверка | да |
| Визуализации | B (обложки/схемы) | средний | да |
| Описание кластера | B — паспорт кластера | средний | да |
| Формулировка выводов | B | высокий | частично |

Модель возьмёт ту таблицу, которая ближе к концу контекста, либо смешает обе. Нужна **одна** таблица.

Глубже: **A/B/C — неправильная ось.** Риск — свойство содержания, а не типа задачи. Вывод «кластер состоит преимущественно из библиографических ссылок» требует взгляда на 30 секунд; вывод «эта сугия подразумевает X» требует раввинистической проверки. Обе задачи называются «формулировка выводов». Уровень проверки должен **вычисляться** из содержания артефакта, а тип задачи задаёт лишь дефолт.

### 1.4. §12 математически запрещает достижение цели из §11

§11 требует «стабильный еженедельный выпуск». §12 требует: «не назначай новый выпуск, пока человек явно не подтвердил завершение предыдущего», «не предлагай новый эксперимент», «не расширяй список задач».

При семи последовательных блокирующих гейтах и одном человеке это означает: любая задержка на любом гейте (человек в поездке, неудачный эксперимент, спорный источник) сдвигает публикацию, а начать исследование для следующего выпуска запрещено. **Конвейеризация запрещена явно.** Еженедельный ритм при недельной латентности гейтов и нулевом буфере недостижим — это не вопрос дисциплины, это арифметика.

Правильная формулировка правила: WIP = 1 **на стадию**, а не на систему. Плюс буфер — банк из 2–3 утверждённых исследовательских пакетов. Плохая исследовательская неделя тогда не срывает публикацию.

### 1.5. Семь гейтов не помещаются в заявленный бюджет времени

§3 задаёт ориентир: 30–60 + 30–60 + 30–60 + 20–30 мин ≈ 2–3.5 часа. Но гейтов семь, и каждый — отдельное переключение контекста (реально +10–15 мин на вход в задачу). Гейты 1, 2, 3 (исследование, тезис, источники) смотрят на **один и тот же материал** и разделены искусственно.

Схлопывается в три сессии:

- **Gate C (Commit)** = бывшие 1+2+3, один пакет: паспорт кластера + доказательная выборка + предлагаемый тезис;
- **Gate S (Script)** = бывший 4;
- **Gate P (Publish)** = бывший 6.

Gate 5 (Recording) — не гейт, а задача: человек не «утверждает» запись, он её делает. Gate 7 (B2B) — не в критическом пути выпуска, это отдельный асинхронный трек.

### 1.6. Пятнадцать агентов — переразбиение

Каждая граница агента — точка сериализации и потери контекста. При этом:

- **Editing Agent** («собирает черновой монтаж, удаляет паузы, синхронизирует экран») — это не LLM-агент вообще, это детерминированный ffmpeg/auto-editor. Называя это агентом, вы приглашаете модель галлюцинировать способность монтировать видео.
- **Story Editor / Script / Human Voice** — это три прохода одного шага сценария, а не три агента.
- **Distribution / Localization** пересекаются на 70%.

Правило: **всё детерминированное — код, не агент.** Агент только там, где нужно суждение. Реалистично: ~6 агентов и ~8 инструментов.

### 1.7. Отсутствуют два агента, которые важнее половины списка

**Adversarial Agent (критик).** Quality Control по описанию проверяет согласованность *пакета* (названия, субтитры, ссылки), но не **валидность утверждения**. Для проекта, чья единственная валюта — доверие, нужен агент, который до человека пытается сломать тезис: ищет альтернативное объяснение кластера (артефакт токенизатора? длина текста? общий редакторский слой?), ищет контрпримеры внутри самого корпуса, проверяет, не является ли «неожиданный результат» известным фактом.

**Provenance Agent.** Промт ни разу не упоминает версионирование корпуса, модели эмбеддингов, индекса и параметров. Между тем весь бренд — «мы публично показываем реальную инженерную работу». **Утверждение «машина сгруппировала так-то», которое нельзя воспроизвести, — экзистенциальный риск проекта**, потому что оно неотличимо от контент-фермы, притворяющейся лабораторией. Нужен `experiment.lock`: хеш снимка корпуса, версия модели эмбеддингов, версия индекса, параметры кластеризации, сид.

### 1.8. У главной декларируемой ценности нет артефакта

«Показывать реальную инженерную работу» — цель, но ни один выходной артефакт её не подтверждает. Завод производит видео, посты, страницы атласа — то есть **высказывания об инженерной работе**. Требование должно быть жёстким: каждый выпуск публикует `experiment/` (конфиг, снимок данных или его хеш, метрики, ноутбук/скрипт), и видео на него ссылается. Побочно это бесплатно решает B2B-доверие: корпоративный клиент смотрит не на ролик, а на воспроизводимый прогон.

### 1.9. Нет пути для отрицательного результата — и это структурный конфликт с §8

Gate 1 требует подтвердить, что «вывод достоин выпуска». Еженедельный ритм требует выпуска каждую неделю. Пересечение этих двух требований — давление на производство значимости, то есть ровно то, что §8 запрещает («искусственное создание сенсации»).

Нужен легитимный формат **null result**: «мы проверили гипотезу, она не подтвердилась, вот данные, вот почему мы ошиблись в ожиданиях». Для лаборатории это не провал, а самый доверительный жанр. Плюс банк тем как буфер.

### 1.10. Запреты не имеют точек принуждения

«Никогда не допускай выдуманные цитаты» — модель не может надёжно контролировать это сама. Запрет без исполнительного механизма — украшение. Каждый пункт §8 должен отображаться в проверку:

| Запрет | Точка принуждения |
|---|---|
| выдуманные цитаты | каждая цитата несёт `source_id` + точный спан; валидатор строкой сверяет со снимком корпуса; нет совпадения — жёсткий блок |
| галахический вывод без проверки | классификатор типа утверждения → маршрут к эксперту, публикация заблокирована до подписи |
| скрытие ошибок модели | обязательное непустое поле `limitations` и `what_failed` в манифесте выпуска |
| буквальный перевод | сравнение EN/RU по структуре и глоссарию + доля дословных n-грамм |
| AI-аватар вместо лица | политика на уровне монтажного пайплайна, а не на уровне просьбы к модели |
| автоответы на чувствительные комментарии | классификатор чувствительности на входе, дефолт — очередь человеку |

### 1.11. Метрики не замыкают петлю

§11 перечисляет девять показателей, но ни один не связан с действием. Метрика без порога и владельца — отчётность, а не управление. Отдельно: «доля автоматизации» в текущей формулировке неизмерима.

Нужно 5–6 **управляющих** метрик с порогом и реакцией (см. §3.8 ниже). Ключевая, которой нет вообще: **rework rate** — доля артефактов, отклонённых на гейте. Если она выше ~30%, проблема не в скорости человека, а в промте агента; это единственный сигнал, отличающий «человек — узкое место» от «машина производит мусор».

### 1.12. Двуязычность недоопределена и это самая скрытая статья затрат

Три требования конфликтуют: «адаптируй, а не переводи» + «не создавай два независимых сценария» + «разделяй русскую и английскую культурную подачу». Если у EN-версии другие аналогии, другой крючок и другая рамка — это **и есть** второй сценарий.

Рабочая модель: инвариантное **исследовательское ядро** (данные, метод, результат, ограничения, ID источников) + два **нарративных слоя** (крючок, аналогии, обращение, CTA). Ядро — один артефакт, слои — два.

И **нерешённый политический вопрос, о котором промт молчит: допустим ли синтезированный голос автора для EN-дорожки?** §8 запрещает AI-аватар в кадре, но про клонирование голоса не сказано ничего. Это развилка с двукратной разницей в стоимости и с прямым влиянием на «доверие» — она должна быть решена явно и записана в политику, а не оставлена на усмотрение модели.

### 1.13. Нет модели стоимости и латентности

«Снижение стоимости производства» — цель из §11, но в промте нет ни бюджета токенов на выпуск, ни распределения моделей по агентам (дорогая модель нужна критику и сценаристу, дешёвая — рерайту описаний), ни политики кеширования корпуса, ни оценки времени прохождения. Для «завода» юнит-экономика — это и есть предмет проектирования.

### 1.14. Что в промте сделано хорошо

Чтобы не выглядело как сплошной разнос:

- десятичастная структура сценария (крючок → проблема → данные → метод → неожиданный результат → ручная проверка → интерпретация → ограничения → переносимость → открытый вопрос) — **сильнейшая часть промта**, её надо оставить почти без изменений; особенно правильно, что разделы 7, 8, 10 закреплены за человеком;
- «не проектируй LMS без подтверждённого спроса» — редкая и полезная дисциплина в промте;
- сама идея гейтов и явного списка того, чего человек делать не должен;
- финальный принцип разделения ответственности сформулирован точно.

## Часть 2. Критика промта №2 (кластер → сценарий)

Промт заметно лучше первого: узкий, с явной схемой вывода, с механизмом исключения примеров и антигаллюцинационными правилами. Проблемы конкретные.

### 2.1. Тайминги противоречат заявленной длительности

Заголовок обещает 3–6 минут, а секции суммируются в 0:00–4:40. Жёсткие таймкоды заставляют модель выдумывать темп, которым она не управляет. Заменить на **бюджет слов**: русская дикторская речь ≈ 130–150 слов/мин, значит 3 мин ≈ 400–450 слов, 6 мин ≈ 800–900. Модель контролирует количество слов, а не секунды.

### 2.2. Самоаттестация вместо проверяемого артефакта

«Отдельно подтверди: все десять центральных примеров были прочитаны» — модель всегда ответит «подтверждаю». Это ритуал, не контроль.

Замена: по каждому из N ID выдать строку `{id, роль: ядро|периферия|исключён, причина}`. Тогда покрытие гарантировано **структурно**, а не обещанием, и исключения становятся рецензируемыми. Общее правило: никогда не просить модель отчитаться о своём процессе — просить побочный продукт процесса.

### 2.3. Однородность оценивается на глаз

«Насколько однородны десять примеров» — без чисел это вкусовщина. В паспорт кластера должны входить силуэт, расстояния каждого примера до центроида, расстояние до ближайшего соседнего кластера. Тогда суждение об однородности опирается на данные, а исключение примера имеет порог, а не настроение.

Отдельно: **схема паспорта кластера в промте №1 нигде не определена**, хотя промт №2 её потребляет. Это разрыв контракта между двумя частями системы.

### 2.4. Цитаты не привязаны к источнику машиночитаемо

Запрет «не выдумывай цитаты» есть, а формат вывода не требует, чтобы цитата несла `source_id` и точный спан. Требовать: каждая экранная цитата эмитится как `{id, ref, exact_text}`, где `exact_text` скопирован дословно из входа. Тогда валидатор делает точное сравнение со снимком корпуса и запрет превращается в проверку.

### 2.5. Нет пути отказа

Если кластер — мусор (артефакт токенизации, все десять примеров суть колонтитулы), промт всё равно обязывает выдать сценарий («сделай видео о типе текста»). Принуждение к выходу при плохом входе — прямой путь к контент-ферме. Нужен разрешённый вердикт `NOT_PUBLISHABLE` с причинами и рекомендацией (перекластеризовать, увеличить k, почистить корпус).

### 2.6. Не хватает запрета на ложную атрибуцию

«Не выдумывай цитаты» не покрывает самый вредный сбой в этой предметной области: приписывание названному комментатору позиции, которой нет в переданном тексте. Формально это не выдуманная цитата — это выдуманная позиция. Нужен отдельный явный запрет и отдельная проверка.

### 2.7. Отсутствует терминологическая политика

Нет правил транслитерации, подачи ивритского термина при первом употреблении, сохранения оригинального написания. Это должно жить в **общем глоссарии-файле**, разделяемом с Localization Agent, иначе RU и EN разойдутся в терминах — и это заметят именно те зрители, чьё доверие дороже всего. Глоссарий как системный артефакт в промте №1 не упомянут вообще.

### 2.8. Выход только в прозе

Сценарий отдаётся Markdown-текстом, но дальше его потребляют машины (визуальный агент, монтаж, дистрибуция, QC). Они будут **разбирать прозу обратно** — классическое место входа ошибок. Выдавать JSON (title, hook, beats[], quotes[], on_screen[], expert_checks[], excluded[]) и рендерить Markdown из него, а не наоборот.

### 2.9. Схема сценария расходится со схемой промта №1

Промт №1 обязывает 10 частей, промт №2 даёт 5 битов и теряет ровно доверительные элементы: **метод, ручную проверку, переносимость, открытый вопрос**. Формально это разные форматы (10–15 мин основной выпуск против 3–6 мин производного), но схема должна быть одна с необязательными битами. Минимум: «ограничения» и «открытый вопрос» обязательны в любом формате.

### 2.10. Мелкое

- «десять» захардкожено — параметризовать как N;
- метка «AI-черновик» стоит только в шапке документа; она обязана присутствовать в каждом производном фрагменте (титры, чанки телесуфлёра), иначе теряется при нарезке;
- «не выводи порядок обучения из номера кластера» — отличное правило, стоит перенести и в промт №1 как общий запрет.

## Часть 3. Итоговая архитектура

### 3.0. Принципы

1. Состояние — в файлах под git, не в контексте модели.
2. Утверждение человека — это подписанный коммит/ревью PR, а не фраза в чате.
3. Уровень проверки вычисляется из содержания артефакта, а не назначается по типу задачи.
4. Детерминированное — код. Агент — только там, где нужно суждение.
5. Каждое утверждение несёт доказательство (`source_id` + спан) или помечено как интерпретация человека.
6. Каждый выпуск воспроизводим (`experiment.lock`).
7. Запрет без точки принуждения не существует.
8. WIP = 1 на стадию, а не на систему.

### 3.1. Разделение промта №1 на четыре артефакта

```
POLICY.yaml        политика: матрица риска, точки принуждения, запреты, роли
                   (меняется редко, ревьюится как код)
SPEC.md            устройство завода: стадии, агенты, контракты артефактов
                   (разовый документ, не грузится на каждый ход)
state/issue-NNN.yaml  единственный источник правды по выпуску
operator.md        рабочий промт: прочитать состояние → один шаг → обновить состояние
glossary.yaml      термины RU/EN/иврит, транслитерация
```

Оператор на каждом ходу получает: `POLICY.yaml` + `state/issue-NNN.yaml` + релевантный кусок `SPEC.md`. Не весь завод.

### 3.2. Запись выпуска — единица состояния

```yaml
id: 2026-W31
stage: script            # research|commit|script|record|post|publish|analyze
research_question: "..."
cluster: {id: 412, size: 1873, silhouette: 0.31}
experiment_lock: sha256:...      # корпус, модель эмбеддингов, индекс, параметры, сид
thesis: {text: "...", approved_by: human, at: 2026-07-28T09:12Z}
sources: [{id: bavli:shabbat:31a:3, span: [140,212], verified: true}]
claims:
  - {id: c1, type: technical, text: "...", evidence: [e1,e2], risk: low}
  - {id: c2, type: interpretive, text: "...", author: human, risk: high}
gates: {commit: signed, script: pending, publish: null}
artifacts: {script: ..., master: ..., shorts: [...], atlas_page: ..., ru: ..., en: ...}
blocker: "ожидает Gate S"
next_step: "автор вносит личную позицию в биты 7,8,10"
done_criterion: "gates.script == signed"
null_result: false
```

Git даёт бесплатно: историю, диффы, откат, атрибуцию утверждений. **Гейт = ревью пул-реквеста.** Утверждение получает метку времени, автора и обратимость — то, чего чат дать не может в принципе.

### 3.3. Три гейта вместо семи

| Новый гейт | Поглощает | Вход человека | Бюджет |
|---|---|---|---|
| **Gate C — Commit** | 1 Research + 2 Thesis + 3 Source | один пакет: паспорт кластера, доказательная выборка, отчёт критика, предлагаемый тезис | 45 мин |
| **Gate S — Script** | 4 Script | утверждение сценария + личная позиция в битах 7/8/10 | 45 мин |
| **Gate P — Publish** | 6 Final | просмотр мастера, подпись | 25 мин |
| *(вне критического пути)* | 7 B2B | асинхронно, отдельный трек | — |

Запись (бывший Gate 5) — задача, а не гейт: 45–60 мин.
Итого ≈ 2.5–3 ч в неделю, что укладывается в заявленный ориентир, чего семь гейтов не позволяли.

Дополнительно: **гейт эксперта** (раввинистическая проверка) вызывается не по расписанию, а по срабатыванию классификатора риска — только когда в выпуске есть утверждение типа `halakhic` или `attribution`.

### 3.4. Матрица риска по типу утверждения (заменяет A/B/C и §7)

| Тип утверждения | Кто формулирует | Проверка | Блокирует публикацию |
|---|---|---|---|
| `technical` (метрика, поведение модели) | машина | `experiment.lock` воспроизводится | да |
| `source` (цитата, ссылка) | машина | точное совпадение спана в снимке корпуса | да |
| `attribution` (позиция названного лица) | машина, черновик | эксперт | да |
| `halakhic` | **никто** — формат запрещён | — | жёсткий блок |
| `historical` | машина, черновик | эксперт + оговорка | да |
| `interpretive` (что это значит) | **только человек** | — | да |
| `commercial` (B2B-обещание) | машина, черновик | отдельная подпись | да |
| `formatting` (субтитры, таймкоды, экспорт) | машина | автотест | нет |

Тип задачи задаёт дефолтный тип утверждения; классификатор может его повысить, но не понизить.

### 3.5. Агенты и инструменты

**Агенты (суждение) — 6:**

1. **Research** — кластеры, аномалии, гипотезы, исследовательские вопросы.
2. **Evidence** — слияние бывших Source Verification + Cluster Passport: паспорт с числами, привязка спанов, метки VERIFY, разделение факта и интерпретации.
3. **Adversary** — *новый, критический*: альтернативные объяснения кластера, контрпримеры, проверка «а не известно ли это давно», попытка сломать тезис до человека.
4. **Script** — слияние Story Editor + Script + Human Voice: черновик по 10-частной схеме, бюджет слов, и — главное — **вопросы автору** для битов 7/8/10, которые машина не заполняет.
5. **Localization** — ядро + два нарративных слоя, глоссарий, контроль дословности.
6. **Judge** — слияние Quality Control + B2B-проверки: финальная проверка пакета против `POLICY.yaml`.

**Детерминированные инструменты (код) — не агенты:**

транскрибация · нарезка · субтитры · нормализация звука · вертикальные версии · экспорт · загрузка · планировщик публикаций · сбор аналитики · валидатор цитат · классификатор типа утверждения · рендер атласа · propagation-движок ретракций.

**Provenance** — не агент, а слой: пишет `experiment.lock` на каждом исследовательском прогоне.

Сокращение с 15 «агентов» до 6 агентов + 13 инструментов снимает большую часть галлюцинаций способностей и большую часть счёта за токены.

### 3.6. Конвейер

```
корпус (снимок, хеш)
  └─ Research ──► кандидаты кластеров ──► Evidence ──► паспорт + спаны
                                              │
                                       Adversary ──► отчёт «почему это может быть неверно»
                                              ▼
                                    ╔══ Gate C ══╗   ← человек: тема, тезис, источники
                                              ▼
                                          Script ──► сценарий + вопросы автору
                                              ▼
                                    ╔══ Gate S ══╗   ← человек: позиция в битах 7/8/10
                                              ▼
                                      запись (человек в кадре)
                                              ▼
                        детерминированный пост: монтаж · субтитры · главы · shorts
                                              ▼
                        Localization ──► RU-слой · EN-слой (ядро общее)
                                              ▼
                                          Judge ──► отчёт соответствия POLICY
                                              ▼
                                    ╔══ Gate P ══╗   ← человек: подпись
                                              ▼
    публикация: выпуск · shorts · статья · LinkedIn · Telegram · атлас · experiment/
                                              ▼
                              аналитика ──► банк тем следующего цикла
```

Все производные — **представления** одного исследовательского ядра с объявленными зависимостями (см. 3.7), а не независимые процессы.

### 3.7. Распространение ретракции — то, чего нет в исходном промте

Проект, продающий доверие, обязан уметь отзывать утверждение. Если через месяц выяснится, что утверждение `c2` было ошибкой, система должна знать **все** производные артефакты, которые на него опираются: тайм-код в выпуске, конкретный short, абзац статьи, поле страницы атласа, слайд B2B-кейса.

Реализация: граф `claim → artifact`. Пометка `claims[c2].status = retracted` порождает задачу на каждый зависимый артефакт и автоматически проставляет пометку на странице атласа с историей изменений. Публичная лаборатория, которая умеет отзывать свои утверждения, получает больше доверия, чем та, которая никогда не ошибается.

### 3.8. Управляющие метрики (с порогом и реакцией)

| Метрика | Цель | Тревога | Реакция |
|---|---|---|---|
| минуты автора на выпуск | ≤ 180 | > 240 | найти стадию-пожиратель, усилить агента |
| **rework rate** (отклонено на гейтах) | < 20% | > 30% | чинить промт агента, а не темп человека |
| латентность гейта p50 | < 24 ч | > 48 ч | резать пакет на гейт, не человека |
| дефекты, пойманные до публикации | ≥ 95% | < 90% | усилить Judge/валидаторы |
| дефекты после публикации | 0 | ≥ 1 | ретракция + разбор + новая проверка |
| стоимость выпуска (машина) | — | рост > 30% м/м | распределение моделей по агентам |
| глубина банка тем | 2–3 | < 1 | приостановить производные, вернуть ресурс в research |

Ритм-метрики (retention, органика, B2B-лиды) — наблюдаемые, не управляющие: они не должны напрямую менять производственные решения, иначе оптимизационная функция §11 подменяется просмотрами.

### 3.9. Формат ответа оператора

**Дефолт — рабочий режим, 6 строк:**

```
Выпуск: 2026-W31 · Стадия: script
Задача: внести позицию в биты 7,8,10
Блокер: Gate S ждёт автора (18 ч)
Машина сделала: черновик сценария 1240 слов, 4 вопроса автору
Следующий шаг: ответить на 4 вопроса в state/issue-2026-W31.yaml
Done: gates.script == signed
```

**Отчётный режим (12 секций исходного §10) — только по явной команде `/report`.** Это устраняет главный операционный дефект промта №1 и не теряет его структуру.

### 3.10. Порядок внедрения

| Этап | Что | Почему первым |
|---|---|---|
| 0 | `state/issue.yaml` + git-гейты | без состояния всё остальное — фикция |
| 1 | `POLICY.yaml` + единая матрица риска | снимает противоречие §1↔§7 |
| 2 | Валидатор цитат + `experiment.lock` | превращает главные запреты в проверки |
| 3 | Три гейта, банк тем, WIP на стадию | делает еженедельный ритм достижимым |
| 4 | 6 агентов, детерминированный пост | снижает стоимость и галлюцинации |
| 5 | Localization: ядро + два слоя | после решения по синтезу голоса EN |
| 6 | Граф ретракций + атлас | масштабирование доверия |
| 7 | B2B-трек, аналитика | только после стабильных 6–8 выпусков |

### 3.11. Решения, которые должен принять человек до запуска

1. **Синтезированный голос автора для EN-дорожки — да или нет.** Влияет на стоимость вдвое и на позиционирование; в политике должно быть записано явно.
2. **Кто эксперт по галахическим и историческим утверждениям**, какова его SLA. Без имени и срока гейт эксперта — фикция.
3. **Снимок корпуса**: источник, лицензия, периодичность обновления, политика цитирования.
4. **Порог отрицательного результата**: при каком условии выпуск публикуется как null result, а не откладывается.
